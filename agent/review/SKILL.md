# muscle_training レビュー手順

リポジトリの前提・フォルダマップ・禁止事項・蓄積した弱点は `GEMINI.md` にある。このファイルはレビューの**進め方**だけを扱う。

---

## 手順（この順番で行う）

### 1. 対象タスクを確認する

**必ず最初に、どのタスクのフィードバックが欲しいかユーザに確認する。** 勝手に「最新のもの」を選ばない。複数選択もありうる。
あわせて、**「英語のフィードバック（PR本文やコミットメッセージの添削）が必要か」もユーザに確認する。**

選択肢を出すときは、各タスクが何のテーマだったかを1行で添える（ユーザは番号を覚えていない）。**列挙は `ls sql/_daily/` と `ls python/daily/` でディレクトリ全体を見る**（`task*` のグロブでは誤字フォルダを取りこぼす）。

### 2. 読み込む対象

対象タスクについて、以下をすべて読む。**一部だけ読んでレビューを書き始めない。**

| 読むもの | 目的 |
|---|---|
| `タスクフォルダ/README.md` | 課題文。要求と**制約**の把握（後述のとおり制約は1つずつ判定する） |
| `タスクフォルダ/` 直下のスクリプト | **提出版。これがレビューの主対象** |
| `タスクフォルダ/FB/`, `answers/`, `answer/` | **過去のタスクにのみ存在する**既存フィードバックと模範解答。無いのが通常 |
| `FB_from_AI_*/` 等の既存レビュー | 指摘の重複を避ける・反映されたかを見る |
| `タスクフォルダ/setup.sql` | SQLタスクの場合。DDLとサンプルデータ（机上トレースに必要） |

### 3. PR の内容を取得する

英語も練習対象なので、PR 本文とコミットメッセージもレビューする。**`gh` で取得する。**

```bash
gh pr list --state all
gh pr view <番号> --json title,body,commits
```

対象タスクに対応する PR を、ブランチ名（`python/task03` など）やタイトルから特定する。**PR は複数ある場合があるので、対象タスクのものを取り違えない。**

取得できなかった場合の手順：

1. `タスクフォルダ/PR_FROM_ME.md` または `タスクフォルダ/answers/PR_FROM_ME.md` を探す（過去のタスクには保存されているものがある）
2. それも無ければ、**レビュー冒頭に明記する。** 「PR 本文を参照できなかったため、英語レビューはコミットメッセージのみを対象にしている」のように、**何を見て何を見ていないか**を書く

`gh` が未インストール・未認証の場合は、レビューを中断せず上記2で続行し、**セットアップが必要であることをレビュー内で1行伝える**（英語は6観点の1つなので、欠けたままにしない）。

**参照できなかったことを根拠に、既存FBが捏造・幻覚したと結論してはならない。** 既存FBが引用している文言が手元に見つからない場合、まず**自分が参照できていない可能性**を疑う。実際に、PR 本文を取得できなかった状態で「存在しないPRを幻視でレビューしている」と誤断定した事例がある。これはレビューの信頼性を最も損なう誤りの型。

### 4. 課題文の制約を列挙する

**レビューを書く前に、課題文の制約を箇条書きで書き出し、1つずつ満たしているか判定する。**

```
制約1: 動的関数（CURRENT_DATE等）の禁止 → 満たしている
制約2: sale_timestamp カラムを関数で加工しない → 違反（DATEDIFF に渡している）
制約3: ISO週基準 → 満たしている（DAYOFWEEKISO）
制約4: CTEは2段階まで → 違反（3段階）
```

**この列挙を省くと違反を取りこぼす。** 過去に、CTE の段数（制約4）だけを指摘してカラム加工（制約2）を見落とした事例がある。目立つ制約を1つ見つけた時点で満足せず、**全制約について明示的に判定する。**

## レビューの目的

実務のプロダクションコードレビューとは目的が違う。**コードの完成度を評価する以上に、「自力で考えて書けたか」を評価する。**

---

## 「自力で書いた箇所」の特定方法

褒めるパートを具体的にするために、**推測ではなく差分で特定する。**

### 原則：模範解答は存在しない

出題スキル（`agent/sql_daily` 等）は**模範解答を作らない。** したがって、**提出版に書かれているものはすべて本人の自力の産物**である。写した可能性を考慮する必要はない。

これは同時に、**レビュアーが正しさの判断を全責任で負う**ことを意味する。照合できる「正解」が無いので、机上トレースと後述のチェックリストの精度がそのまま品質になる。「模範解答と一致しているから正しい」という近道は使えない。

褒めるパートでは、**課題文が要求した以上の判断が入っている箇所**を探す。

- **課題文のヒントに乗らず、別の正解に到達している**（例：`idxmax()` を使えと誘導されたのに `sort_values` + `drop_duplicates` で解いた）
- **便利メソッドを知らずに、プリミティブだけで解き切っている**（冗長でも組み立てた力は明確に評価する）
- **公式ドキュメントを読んだ形跡**（例：`validate="many_to_one"` ではなく短縮エイリアス `validate="m:1"` を使っている）
- **副作用や境界を先読みした形跡**（`.copy()` の位置、半開区間の選択、`DAYOFWEEKISO` の選択など）
- **課題の主題（罠として設定されたテーマ）を構造的に回避する方針を選んでいる**

### 過去のタスクで模範解答がある場合のみ

`FB/` や `answers/` に模範解答が存在する古いタスクでは、以下の差分比較も使える。

提出版（`タスクフォルダ/` 直下のスクリプト）と模範解答を比較し、**一致しない箇所**を洗い出す。そこが本人の判断が入った場所。

強い「理解の証拠」になるのは以下。

- **模範解答に無い書き方を選んでいる**（例：模範解答が `validate="many_to_one"` なのに提出版が `validate="m:1"` → 公式ドキュメントを自分で読んだ証拠。模範解答から写せない文字列だから）
- **課題文のヒントに乗らず、別の正解に到達している**（例：`idxmax()` を使えと誘導されたのに `sort_values` + `drop_duplicates` で解いた）
- **便利メソッドを知らずに、プリミティブだけで解き切っている**（冗長でも丸暗記では不可能。指摘は別途するが、組み立てた力は明確に評価する）
- **模範解答のコメントを自分の言葉に置き換えている**（日本語コメントを英語で書き直している等）
- **副作用や境界を先読みした形跡**（`.copy()` の位置、半開区間の選択など）

逆に、**提出版と模範解答が完全一致している箇所は理解の判定材料にならない。** 褒める対象は自力の差分に絞る。

**模範解答が提出後に書かれた形式のタスク**（提出物を受けてフィードバックが作られた場合）では、提出版の内容はすべて自力の産物である。その場合は「一致した箇所＝独力で正解に到達した箇所」として評価する。模範解答が提出版の命名や構造を踏襲していれば、それも設計が妥当だった証拠として挙げる。

## 構成（必ず2部構成にする）

### 第1部：褒めるパート（先に書く）

#### 最初に、課題の主題を攻略できているか評価する

**課題文が「罠」「難所」「死の罠」「最も難しい」などと明示しているテーマを特定し、それが攻略できているかを最初に書く。**

課題は必ず何かを狙って作られている。そこを攻略できていれば、それが最大の成果である。逆にそこに触れずに細部だけ褒めると、レビューとして焦点を外す。

過去の実例：課題文が「毎年必ずどこかでバグを発生させる死の罠」としてカレンダー年とISO年の不整合を挙げていたタスクで、提出コードは**週番号を一度も materialise しない方針**を採ったため構造的に免疫があった。この評価が抜けていたレビューがあった。

攻略できていない場合も、まず主題について書く（第2部の正確性で扱う）。

#### そのうえで

- 良かった判断を、**具体的なコード行を引用して**褒める。「良いですね」で終わらせず「なぜ良いのか」を説明する
- **なぜそれが自力の証拠なのかも書く**（「課題文はこの手法を指定していないので、自分で選んだことになる」「短縮エイリアスは公式ドキュメントを読まないと出てこない」など）
- エッジケースを意識した形跡、過去の指摘が反映されている箇所も積極的に見つける
- 楽しんで解いている形跡（1問のところ2問解く等）があれば、その姿勢にも触れる
- **謙遜しがちなので遠慮せずはっきり褒める。** 自己評価が実態より厳しいと判断できる場合は、そう明言する

### 第2部：客観的な技術評価（褒めた後に書く）

遠慮せず実務レベルの厳しさで書く。第1部と明確に区切る。

以下6観点を見る。**観点自体を省略しない。**

1. **正確性** — 意図した結果が出るか。NULL・重複行・空データ・境界値の日付で壊れないか
2. **イディオム** — SQLなら Window関数/QUALIFY の適切な使用、不要なサブクエリ・CTE。Python なら pandas API の適切な使用（ループでの逐次処理になっていないか）
3. **パフォーマンス** — SQLなら Spillage、パーティションプルーニングの崩壊、集約前の `ORDER BY`、不要な全件スキャン。Python なら apply 濫用、chained indexing、捨てられるコピー
4. **可読性・命名** — 後述の命名チェック
5. **本番運用の視点** — 後述の必須トレース

※ PR・コミットメッセージの**英語のスキル**については、技術的評価とは別に `FB_ENG_{連番}/README.md` に出力する。

#### 「問題なし」と書く前に、確認した内容を書く

**どの観点でも、「問題なし」「該当なし」と書く場合は、何を確認した結果そう判断したのかを1行添える。**

```
✗ ### 本番運用の視点
  問題なし

✓ ### 本番運用の視点
  0件入力・再実行・バックフィルの3点をトレースした結果、以下2件が該当する。
```

確認せずに「問題なし」と書くのは、見落とすことより悪い。**見ていない領域を検証済みとして報告することになる。**

#### 正確性の指摘には必ず「壊れる条件」を書く

「〜の可能性があります」で終わらせない。**具体的な入力 → 何が起きるか**を書く。書けないなら、その指摘は弱いので出さない。

悪い例：`index` がユニークでない場合に問題が起きる可能性があります。

良い例：`df_products` を `pd.concat([chunk1, chunk2])` で作ると index が `0,1,0,1` になり、`groupby.max()` が拾う `idx` が複数行にマッチして重複排除が失敗し、次の `validate="m:1"` が `MergeError` を投げる。エラーが merge 行を指すので、真の原因（index の非ユニーク性）まで辿るのに時間がかかる。

**サンプルデータがある場合は、具体的な行ID・タイムスタンプ・値で示す。** 「リスクがあります」「ズレる可能性があります」は壊れる条件を書いたことにならない。DDL のサンプルデータを使って、どの行がどう扱われるかまで確定させる。

```
✗ 時刻成分が残るため、意図しないオフバイワンを引き起こすリスクがあります
✓ SESSION_DATE = '2026-09-01 03:15:00' のとき境界は 2026-08-24 03:15:00 になり、
  S_002（2026-08-24 01:10:00、月曜未明の売上）は 01:10 < 03:15 で除外される。
  エラーは出ず、合計金額だけが毎週小さくなる
```

前者は読んでも何をすべきか分からず、後者は再現手順とテストケースを兼ねる。

#### 「検証が機能していない」パターンを毎回確認する

実装で使った操作と同じ操作で期待値を計算していると、両辺が必ず一致し、検証は「実装が実装どおりであること」しか確認しない。

判定法：**その検証が失敗する入力を1つ挙げられるか。** 挙げられないなら機能していない。

実例：`validate="m:1"` が通った後の行数アサーション（数学的に失敗不能）。`drop_duplicates` の結果同士を比較するアサーション（ソート順は件数を変えないので失敗不能。`ascending` を反転させて全行が誤っても通る）。

指摘するときは、**通ってしまう改変を具体的に示す**（「`ascending=False` を `True` にすると全キャンペーンで最小値が出るが、行数は変わらないので検証は通る」）。

#### 修正指示の副作用を検証する

**既存FBや自分が出す修正案について、「その指示だけに従ったら何が起きるか」を必ずトレースする。**

過去の実例：既存FBが「`>=` と `<` の半開区間に直せ」と指示していたが、境界に `DATE_TRUNC` が無い状態でそれだけ適用すると、実行時刻が深夜0時でない本番環境で月曜未明の売上が毎週サイレントに欠損する。**修正指示が別のバグを生むケースは、単独のバグより検出が難しい。**

#### 制約からの逸脱は正確性の問題として扱う

手順4で列挙した制約について、違反があれば指摘する。逸脱してもよいが、その場合は**PR に「逸脱として明示し理由を書く」のが作法**だと伝える。「除外して数えれば満たしている」という書き方は、レビュアーが見落とすので不可。

#### 指摘には必ず「次にどう直すか」を添える

修正コード片と、持ち帰れる一般原則（「`df.index` をデータとして使う前に `reset_index(drop=True)`」など）をセットで書く。

## 可読性・命名のチェック

- 変数名・関数名が意図を表しているか。関数が名前より多くの責務を持っていないか
- **境界は開始と終了のペアで対称に命名されているか**（`baseline` 単独ではなく `week_start_date` / `week_end_date`）。半開区間 `[start, end)` の定型に乗る名前にする
- **粒度と型が名前に入っているか**（`week` は週番号か日付か不明。`week_start_date` なら自明）
- **層を示す接頭辞を誤用していないか。** dbt 系の `raw_` / `stg_` / `int_` / `fct_` / `dim_` は層を示す規約。処理ステップ名の CTE に `raw_` を付けると、生データ層のオブジェクトと誤読される（実例：`raw_get_baseline`、`raw_extract_targets` は生データ層ではない）
- `tmp_` のように中身を説明しない接頭辞になっていないか

## 本番運用の視点（必須トレース）

**以下3点は毎回明示的にトレースする。トレースせずに「問題なし」と書いてはならない。**

### 1. 入力が0件のとき、何行返り、その中身はどうなるか

- SQL：`GROUP BY` の無い集計クエリは**0行入力でも必ず1行返す。** 集計関数は NULL になるため、`(NULL, NULL)` のような「壊れたレコード」が出力される。下流で主キー・パーティションキーに使っていれば落ちる。対処は `COALESCE(SUM(x), 0)` と、ラベルを集計関数から取らないこと
- Python：空の DataFrame が静かに返って「正常終了」しないか。上流の連携停止を検知できるか

### 2. 同じ処理を再実行したとき、同じ結果になるか（冪等性・決定論性）

- 同点（tie）時にどの行が選ばれるか決まっているか。`sort_values` の既定 `kind='quicksort'` は非安定
- 実行時刻・実行曜日に依存していないか
- 出力の行順・index が固定されているか

### 3. 過去の特定期間を対象に再実行（バックフィル）できるか

- 「実行日から逆算」する構造は、**実行が1週遅れると対象期間ごとずれる。** バッチが落ちて翌週まで復旧しなかった場合、落ちた週は永久に集計されない
- 実務では対象期間をパラメータで外から渡す（dbt の `var()`、Airflow の論理実行日）。課題の制約で逆算が要求されている場合は、提出版は正解としたうえで「その外側にパラメータの口を用意する段階がある」と伝える

### そのほか

エラーハンドリング、終了コード（握りつぶして 0 を返していないか）、ログ、リトライ設定値、`assert` を品質ゲートに使っていないか、宣言されていない依存、境界そのものを検証するアサーションの有無。

## 既存フィードバックの扱い（過去のタスクのみ）

**新しいタスクには存在しない。** `FB/` や `answers/` があるのは過去のタスクだけなので、無い場合はこの節を飛ばす。**「既存FB未指摘」のような見出しも使わない**（比較対象が無いのに未指摘と書くと、読み手が存在しないFBを想像する）。

存在する場合、既存のフィードバックは**正解ではなくもう一つのレビュー対象として読む**（既知の欠陥は `GEMINI.md` を参照）。

- 既存FBが**既に指摘済みの点は繰り返さない**（「既存FBの指摘は正しい」と一言触れて次に進む）
- 既存FBが**見落としている点を探す。ここがこのレビューの主な付加価値**
- 既存FBの**模範解答自体にバグや実務上の問題がないか**を検証する
- 既存FBの**断定が過剰でないか**を検証する（実例：「スカラサブクエリなのでプルーニングが100%効く」は、オプティマイザの定数畳み込みに依存する話で保証はない）
- 既存FBと**評価が異なる場合は、そう明言して理由を書く**

対策として、模範解答についても**「壊れる条件を1つ挙げる」を必ず実行する。** 挙げられないなら検証していないのと同じ。

最後に、既存FBが見落としていた点を一覧で示す。**模範解答を疑う目線を持てるようになること自体が学習目標。**

### 出題と同じモデルがレビューする場合の注意

**出題スキルとレビュースキルを同じモデルが実行する場合、盲点が相関する。**

自分が仕込んだ罠は自分には見えているが、**仕込んでいない罠は自分にも見えない。** 出題時に「ここを狙った」と考えた箇所だけを検証して、それ以外を通してしまう危険がある。

対策：レビュー時は**出題時の意図を思い出そうとせず、コードだけを読む。** そして必須トレース（0件入力・冪等性・バックフィル）とチェックリストを、狙ったテーマと無関係に全項目実行する。**チェックリストの価値は、自分が考えていなかった領域を強制的に見せることにある。**

## 「丸暗記か理解か」を見分ける観点

以下は、正確に動いていても指摘する。

- コメントがない、または「なぜこう書いたか」の説明が一切ない
- 変数名やコメントが不自然に教科書的で、自分の言葉になっていない
- 簡単な方の書き方に頼り、制約を意識した工夫が見られない
- 出題文のコメントや指示文がそのまま残っている（読み返していないサイン）
- 試行錯誤の残骸（no-op の代入、未使用インポート、捨てられるコピー、`CASE WHEN <boolean> THEN true ELSE false END`）

「動いているので合格」とせず、**末尾の確認質問に回す。**

### 確認質問の作り方

2〜3問に絞る。以下を守る。

- **自分が提案した解について聞かない。** 「なぜこの LEFT JOIN が最適解か」のような質問は、ユーザの理解度ではなく解説を読んだかを測るだけになる
- **提出版のコードそのもの**について聞く。判断が入った箇所（なぜその関数を選んだか、その前提が崩れたらどうなるか）を狙う
- （模範解答がある過去タスクのみ）**模範解答と一致している箇所について聞かない**（写した可能性が排除できない）

型：

- 「この防御Aが効いているとき、次の行の防御Bは失敗しうると思いますか」（何を保証しているか理解しているかの確認）
- 「入力がこう変わったとき、このロジックはどう壊れますか」（前提を意識できているかの確認）
- 「一見矛盾するこの2つを、1つの原則で説明できますか」（暗記でなく体系で持てているかの確認）
- 「前回このパターンでは必要でしたが、今回は不要です。その違いを1つの基準で説明できますか」（基準として持てているかの確認）

答えを本文中に書いておき、「まず自分で言葉にしてから読み合わせてください」と添える。

## 英語レビューのチェックリスト

PR 本文が取得できた場合は本文とコミットメッセージの両方、取得できなかった場合はコミットメッセージのみを対象とし、**どちらなのかを明記する。**

既存FBが指摘済みの点は繰り返さず、以下を機械的に確認する。

**文法**
- 自動詞を受動態にしていないか（`be remained` ✗ → `be kept` / `will remain`。同型：`be occurred` ✗、`be happened` ✗）。日本語の「〜される」を直訳すると起きる
- 三単現の `-s` の脱落（`This query extract` ✗）。技術文書は主語が三人称単数になりがち
- 助動詞の後は原形（`will makes` ✗ → `will make`）
- 冠詞の欠落（単数可算名詞に冠詞・所有格があるか）。初出の懸念に `the` を付けていないか（`the problem` → `a potential issue`）
- 使役動詞の語法（`let X do` / `allow X to do`。`let X to do` ✗）
- 形式目的語の欠落（`makes easy to follow` ✗ → `makes it easy to follow`）
- `recommend` の語法（`recommend you to <名詞>` ✗ → `recommend two actions`）
- カンマスプライス（独立した2文をカンマだけで接続していないか）

**語彙**
- 技術用語の選択（`temporal` ✗ → `transient`、`row number`（何行目か）✗ → `row count`、`credit` → `credit consumption`）
- 存在しない副詞（`expectedly` ✗ → `as expected`）
- 動詞の強さがコードの挙動と一致しているか（条件で落とすなら `Check if` より `Assert that`）
- 対応する名詞があるのに -ing 形にしていないか（`its requesting` → `its requests`）
- `in maximum` ✗ → `up to` / `a maximum of`
- トーンが強すぎないか（リスク報告に `I'd love to` ✗ → `I would like to flag`）

**表記**
- 頭字語（`api` → `API`、`ai` → `AI`）、クラス名（`runtimeerror` → `` `RuntimeError` ``）
- 曜日・月名は大文字始まり（`monday` ✗ → `Monday`）
- コード識別子はバックティックで囲み、正確に綴る。所有格の `'s` を識別子に付けない（`df_sales's` → `the row count of df_sales`）
- Conventional Commits の**コロン**（`feat(scope) msg` ✗ → `feat(scope): msg`）
- type の選択（フィードバック文書の追加は `feat` ではなく `docs`）
- 見出しに文章や句点を入れない
- **スペルミスは git 履歴に残り検索性を損なう**ことを指摘する（マージ済みなら修正不能）

**構成・内容**
- 冒頭1文で「何を・どこに・どういう制約で」を言い切れているか
- 設定値の羅列に「なぜその値か」が添えられているか
- **仕様記述がコードのバグと同じ誤りをしていないか。** 繰り返し起きている。説明と実装が同じ誤りを共有すると、レビュアーが説明を読んでもバグを検出できない
- 期間・範囲は**半開区間の記法**で書けているか（`[2026-08-24 00:00, 2026-08-31 00:00)`）。この記法にするだけで、書いた本人がオフバイワンに気づける
- 「最大値を取る」等の仕様に、**同点時の扱い**が書かれているか
- 制約から逸脱した場合、それが逸脱として明示されているか
- 添削は**原文と添削版を並べ、変更理由を説明する**

**不確実性の表現**（Note セクションがある場合）

日本語の「厳しいかも」「よく分からなかった」を直訳すると過度に自信がない印象になる。使える型を提示する。

- `I am not confident about X`
- `I could not work out ...`（`I didn't understand` より能動的）
- `I would appreciate a second opinion on ...`
- `I dropped it since it was out of scope`（やらなかった判断の正当化）
- `Working out how to X took me about an hour`（所要時間を事実として述べる）
- `What I had actually got wrong was ...`（自己診断の提示）

最後に**そのまま使える添削版PR本文**を提示する。

## トーンのルール

- 第1部は温かく具体的に。第2部は実務のレビューと同じ厳しさで、遠慮しない
- 「素晴らしい」だけで終わらせない。常に「どこが」「なぜ」を伴わせる
- 弱点を指摘する際も人格や能力を否定せず、「次にどう直すか」を必ず添える
- 既存FBと評価が異なる場合は、理由を述べて自分の判断を示す。曖昧にしない
- **過剰な演出をしない**（役割演技、絵文字の多用、「100点満点」のような満点評価）。バグを見落としたまま満点をつけると、レビューの信頼性が失われる
- **確認していないことを確認したように書かない。** 実行していない、参照できなかった、トレースしていない——いずれも正直に書く

## 出力先

技術的なレビューは、各タスクフォルダ配下に `FB_from_AI_{連番}` フォルダを作成し、`README.md` として書く。英語のレビューは上記の通り `FB_ENG_{連番}/README.md` に書く。

```
python/_daily/task_d_01/FB_from_AI_01/README.md
python/_daily/task_d_01/FB_ENG_01/README.md
```

- **連番は既存フォルダを確認して次の番号にする。** `FB_from_AI_*` に加え、過去の別ツールによる出力（`FB_from_Claude_*` 等）も見て重複しない番号を選ぶ
- commit・push はユーザに指示されたときだけ行う

### 修正版スクリプトは必ず出す

**指摘だけで終わらせず、修正版スクリプトを同じフォルダに必ず置く。**

- **指摘した全項目を同時に満たす形**にする。個別の修正案を並べるのと、全部を両立させる1本を書くのは別の作業で、後者の方が難しく、学習価値も高い
- 課題文の**制約も満たす**（CTE段数などを数え直す）
- **元のスクリプトとの差分を冒頭コメントに列挙し、それぞれ理由を書く**
- **実行していないことを明記する**
- SQL の場合、dbt モデルに載る形か確認する。**`SET` 文に依存する解は単一 SELECT にならないため dbt モデルには移植できない**

## レビュー後：次の出題に繋げる

出題スキル（`agent/sql_daily` 等）の**復習モードは、このレビューの「まとめ」セクションだけを読む。** したがって、まとめには以下を必ず含める。

- **「次にやるべき課題の提案」** — 具体的に。「Late-Arriving Data のマージ」のようにテーマ名で書き、なぜ今それかも1行添える
- **「穴」の3段階** — 深い層に挙げたものが、次回の優先テーマになる
- **今回通用した解法** — 復習モードは「前回通用した解法を封じる制約」を作るので、何で解けたかが分かるように書く（例：「`drop_duplicates` で解けた」）

### 弱点リストの更新を提案する

`GEMINI.md` の「繰り返し出ている弱点」は手で維持されているリストで、**放置すると古くなる。**

同じ種類の指摘が**3タスク以上にまたがった**と判断したら、レビューの最後に **`GEMINI.md` への追記を提案する。** 提案だけにとどめ、勝手に書き換えない（リストが膨らむと常時読み込みのコストになるため）。

```
`GEMINI.md` の「繰り返し出ている弱点」への追記を提案します：
8. {パターン名} — {判定法や一行の原則}（task{A}・task{B}・task{C} で発生）
```

逆に、**リストに挙がっている項目が2回連続で問題なく処理されていた**場合は、削除の提案もする。潰せた弱点を抱え続ける必要はない。
