# レビュープロファイル：Python Weekly（抽出・検証・可視化）

`python/_weekly/task_w_{NN}/` のレビューで、手法ファイル（`review_1_correctness` / `review_2_quality`）と**併せて読む。**

## 実行の可否

**実行してよい。** ローカル実行にコストがかからない。

```bash
uv run python python/_weekly/task_w_{NN}/main.py
```

**ただしモックAPIが外部（`httpbin.org` 等）を叩く場合、実行はネットワークアクセスを伴う。** 課題がダミー関数で完結している場合は問題ない。外部を叩く構成なら、実行するか机上に留めるかを判断し、**どちらにしたかを明記する。**

**実測値と机上トレースを区別して書く。** 実行した場合は「実行して確認した」と明記する。

## 読む対象

| ファイル | 目的 |
|---|---|
| `README.md` | 課題文。要求と3フェーズの条件。**モックAPIのコードもここにある** |
| `main.py` 等の提出スクリプト | **提出版。レビューの主対象。複数モジュールに分かれている場合は全部読む** |
| **`plots/*.png`** | **可視化の成果物。画像として読み込んで中身を評価する** |

複数ファイルに分かれている可能性がある（`extract.py` / `validate.py` / `visualize.py` など）。`ls -R` で確認してから読む。

## 3フェーズすべてを評価する

Weekly は**抽出・検証・可視化の3フェーズ**が課題の構成要素。**どれか1つでも評価が抜けたらレビューとして不完全。**

### 抽出フェーズ

- **リトライ上限が有限か** — 無引数の `@retry` は無限リトライ（`stop_never`）
- **`stop_after_attempt(N)` は「試行N回」であって「リトライN回」ではない**（初回1回 + リトライ N-1 回）。課題の要求と合っているか
- **リトライ対象を絞っているか** — `retry_if_exception_type` で 429 / 503 のみ。**401 や 400 をリトライしていないか**（恒久エラーなので待つだけ無駄）
- **Jitter が入っているか** — 固定間隔だと全クライアントが同期して相手を叩き続ける（thundering herd）
- **`timeout` を指定しているか** — 応答が返らない障害では例外が出ないためリトライが発動しない。**リトライとタイムアウトは必ずセット**
- **`reraise=True` の有無と、その後の扱い** — 上まで飛ばした例外を `except Exception` + `print` で握りつぶすと**終了コード0（成功）を返す**。オーケストレータが「成功」と誤判定するサイレント障害
- **リトライが観測できるか** — `before_sleep_log` が無いと本番でリトライは不可視になる

### 検証フェーズ（Polars）

**pandas ではなく Polars。挙動が違う部分が評価の要点。**

- **`null` と `NaN` を区別する** — Polars は別物として扱う（pandas は混同する）。`null_count()` と `is_nan()` を使い分けているか
- **`collect()` の位置** — `LazyFrame` で組んだ式を早く `collect()` すると遅延評価の利点が消える。フィルタや列選択より前に collect していないか
- **式の連鎖** — `pl.col()` の式を組み立てる形になっているか、行ごとの `apply` で回していないか
- **strict な型** — Polars は暗黙キャストをしない。`cast(strict=False)` を安易に使って失敗を潜在化させていないか
- **0件レスポンス** — 空の JSON が返ったとき、後続が静かに通ってしまわないか。`describe()` は空でも動くため検知できない
- 欠損カウント・基本統計量が**課題の要求どおり算出されているか**

### 可視化フェーズ（Seaborn）— 画像を必ず読む

**`plots/*.png` を画像として読み込んで、図の中身を評価する。** コードだけ見て「`histplot` を使っているので OK」で終わらせない。

| 見るもの | 判定 |
|---|---|
| **外れ値が視認できるか** | 1件の外れ値が bins に埋もれていないか。必要なら対数軸か |
| **bins の妥当性** | 既定のままで分布が潰れていないか、細かすぎてノイズになっていないか |
| **軸とラベル** | 軸ラベル・単位・タイトルが読めるか。**デバッグ用途なので数値が読み取れることが要件** |
| **スケール** | 桁が大きく離れた値がある場合、線形軸で潰れていないか |

コード側で見るもの：`plt.savefig()` でファイルに落としているか（`show()` だけだと成果物が残らない）、`plt.close()` でリソースを解放しているか、`figsize` と `dpi` が読める大きさか。

**画像が無い場合**は、レビュー冒頭に「**画像が提出されていないため、可視化フェーズはコードの妥当性のみ評価した**」と明記し、次回は `plots/` に保存することを伝える。

## 命名・構成

- **フェーズが関数として分離されているか** — 抽出・検証・可視化が1つの巨大な関数に混ざっていないか
- 関数が名前より多くの責務を持っていないか
- `tmp_` のように中身を説明しない接頭辞
- 型ヒント、docstring

## 本番運用の必須トレース

| 観点 | 何を見るか |
|---|---|
| **0件入力** | API が空の JSON を返したとき、検証フェーズが静かに通らないか。可視化が空の図を出さないか |
| **冪等性・決定論性** | 同じレスポンスで同じ出力・同じ図になるか。ソートやサンプリングに乱数が入っていないか（`random_state` 未指定） |
| **バックフィル** | 対象期間を引数で受け取れるか。CLI 化されているか |

そのほか：**終了コード**（`sys.exit(1)` を返すか）、`logging` を使っているか（`print` のみでないか）、宣言されていない依存（`uv add` 済みか）、`assert` を品質ゲートに使っていないか。

## 修正版の出力

`FB_from_AI_{NN}/corrected_answer.py`（単一ファイルの場合）または `FB_from_AI_{NN}/corrected/` 配下にツリーで置く（複数モジュールの場合）。

- 指摘した全項目と課題文の全制約を**同時に満たす**こと。**3フェーズすべてを含める**
- 冒頭 docstring に差分を列挙。**実際に変更した行だけ**を挙げる
- **実行して動作を確認し、その旨を書く。** 図を修正した場合は `FB_from_AI_{NN}/plots/*.png` に生成した画像も置く
- コード内コメントは英語で書く
