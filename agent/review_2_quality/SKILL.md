# レビュー Pass 2：品質と伝達

リポジトリの前提・フォルダマップ・禁止事項・蓄積した弱点は `GEMINI.md` にある。

## このパスの担当範囲

**Pass 1（正確性）が完了している前提で実行する。**

| 担当する | Pass 1 が担当済み |
|---|---|
| イディオム・パフォーマンス | 課題の主題の攻略 |
| 可読性・命名 | 褒めるパート |
| 確認質問 | 制約の充足判定 |
| まとめ（3段階の穴・次の課題） | 正確性（壊れる条件） |
| 英語レビュー（PR） | 本番運用の必須トレース |
| | 修正版スクリプト |

---

## 実行のしかた

**Pass 1 とは別のセッションで実行する。**

同じセッションで続けて実行すると、Pass 1 の思考過程がそのまま残っているため、**下記の「Pass 1 を点検する」が機能しない**（自分が出した結論に同意するだけになる）。セッションを分けると、Pass 1 の出力を「他人が書いた文書」として読めるので、抜けや誤りに気づける。

副次的に、Pass 1 と Pass 2 の指示が同時にコンテキストに載らないため、指示の取りこぼしも減る。

**このスキルは単体で完結するよう書かれている。** Pass 1 の記憶は前提にせず、必要なファイルはすべて読み直す。

## 手順

### 1. Pass 1 の出力を読む

**`タスクフォルダ/FB_from_AI_{連番}/README.md` と修正版スクリプトを読む。**

冒頭の進捗行を最初に確認する。

| 進捗行 | どうするか |
|---|---|
| `> 進捗：Pass 1（正確性）まで完了` | **このまま Pass 2 を実行する** |
| `> 進捗：Pass 1・Pass 2 完了` | **実行しない。** 完了済みであることを伝え、何をしたいか確認する |
| ファイルが無い | **Pass 1 が未実施。** その旨を伝え、`review_1_correctness` を先に実行することを提案する |

目的は3つ。

1. **重複を避ける。** Pass 1 が指摘した内容を繰り返さない
2. **まとめの材料にする。** 3段階の穴と「次にやるべき課題」は、Pass 1 の指摘を分類して作る
3. **Pass 1 を点検する。** 読んでいて以下に気づいたら、まとめの前に**1節設けて指摘する**
   - 壊れる条件が「リスクがあります」で止まっている
   - 「問題なし」に確認内容が添えられていない
   - 修正版スクリプトの差分コメントが、実際に変更していない行を挙げている
   - 修正版が制約を満たしていない、または指摘の一部を反映していない

Pass 1 と同じモデルが実行する場合でも、**出力を読み直すと自分の抜けが見える。** これがパスを分けた主目的の1つ。

### 2. 提出版と課題文を読む

`タスクフォルダ/README.md` と提出版スクリプト。Pass 1 の要約だけで判断せず、**コードは自分で読む。**

### 3. PR の内容を取得する

英語も練習対象なので、PR 本文とコミットメッセージをレビューする。**`gh` で取得する。**

```bash
gh pr list --state all
gh pr view <番号> --json title,body,commits
```

対象タスクに対応する PR を、ブランチ名やタイトルから特定する。**PR は複数あるので取り違えない。**

取得できなかった場合：

1. `タスクフォルダ/PR_FROM_ME.md` または `タスクフォルダ/answers/PR_FROM_ME.md` を探す
2. それも無ければ、**何を見て何を見ていないかを明記する。** 「PR 本文を参照できなかったため、コミットメッセージのみを対象にしている」のように書く

`gh` が未インストール・未認証なら中断せず上記2で続行し、**セットアップが必要であることを1行伝える。**

**参照できなかったことを根拠に、既存FBが捏造・幻覚したと結論してはならない。** 引用されている文言が手元に見つからない場合、まず**自分が参照できていない可能性**を疑う。過去に「存在しないPRを幻視でレビューしている」と誤断定した事例がある。これはレビューの信頼性を最も損なう誤りの型。

## イディオム・パフォーマンス

- **SQL** — Window関数/QUALIFY の適切な使用、不要なサブクエリ・CTE、Spillage、パーティションプルーニングの崩壊、**集約前の `ORDER BY`**（順序を保証しないうえに最もスピレージを起こしやすい）、不要な全件スキャン、窓関数の前に絞り込めていないか
- **Python** — pandas API の適切な使用（ループでの逐次処理になっていないか）、apply 濫用、chained indexing、**捨てられるコピー**（`.copy()` の直後に別オブジェクトで上書き）
- **冗長な構造** — `CASE WHEN <boolean> THEN true ELSE false END` は条件式そのものと同じ。`NVL`/`COALESCE` が発動しえない位置に置かれていないか（**dead code なだけでなく、意図が要求と逆のことがある**）

---

## 可読性・命名

- 変数名・関数名が意図を表しているか。**関数が名前より多くの責務を持っていないか**
- **境界は開始と終了のペアで対称に命名されているか**（`baseline` 単独ではなく `week_start_date` / `week_end_date`）。半開区間 `[start, end)` の定型に乗る名前にする
- **粒度と型が名前に入っているか**（`week` は週番号か日付か不明。`week_start_date` なら自明）
- **層を示す接頭辞を誤用していないか。** dbt 系の `raw_` / `stg_` / `int_` / `fct_` / `dim_` は層を示す規約。処理ステップ名の CTE に `raw_` を付けると生データ層と誤読される（実例：`raw_get_baseline`、`raw_extract_targets` は生データ層ではない）
- **名前が実装の誤解を映していないか。** 「日付単位で最新」を意味する名前なのに `partition by store_id` だけ、のような食い違いは、バグの在処を示す
- `tmp_` のように中身を説明しない接頭辞になっていないか

## 「丸暗記か理解か」を見分ける観点

以下は、正確に動いていても指摘する。

- コメントがない、または「なぜこう書いたか」の説明が一切ない
- 変数名やコメントが不自然に教科書的で、自分の言葉になっていない
- 簡単な方の書き方に頼り、制約を意識した工夫が見られない
- 出題文のコメントや指示文がそのまま残っている（読み返していないサイン）
- 試行錯誤の残骸（no-op の代入、未使用インポート、捨てられるコピー）

「動いているので合格」とせず、**確認質問に回す。**

## 確認質問（必ず2〜3問）

**1問で終わらせない。** 以下を守る。

- **自分（および Pass 1）が提案した解について聞かない。** 「なぜこの LEFT JOIN が最適解か」のような質問は、ユーザの理解度ではなく解説を読んだかを測るだけになる
- **提出版のコードそのもの**について聞く。判断が入った箇所（なぜその関数を選んだか、その前提が崩れたらどうなるか）を狙う
- （模範解答がある過去タスクのみ）模範解答と一致している箇所について聞かない

型：

- 「この防御Aが効いているとき、次の行の防御Bは失敗しうると思いますか」（何を保証しているか理解しているかの確認）
- 「入力がこう変わったとき、このロジックはどう壊れますか」（前提を意識できているかの確認）
- 「一見矛盾するこの2つを、1つの原則で説明できますか」（暗記でなく体系で持てているかの確認）
- 「前回このパターンでは必要でしたが、今回は不要です。その違いを1つの基準で説明できますか」（基準として持てているかの確認）

答えを本文中に書いておき、「まず自分で言葉にしてから読み合わせてください」と添える。

## まとめ

### 3段階の穴

Pass 1 と Pass 2 の指摘を、**浅い層＝語彙・作法 / 中間＝その言語特有のモデル / 深い層＝設計思想**の3段階に分けて優先順位をつける。

**層の割り当ては深刻度で決める。正確性の問題（特にサイレントなデータ破損）は、必ずパフォーマンスやイディオムより深い層に置く。** 3段階リストは次回の出題テーマを決めるため、順序を間違えると「壊れるバグ」より「遅いクエリ」を先に潰すことになる。**実際に逆順で書かれたレビューがあった。**

### 出題スキルが読むもの

出題スキルの**復習モードは、このまとめセクションだけを読む。** したがって以下を必ず含める。

- **「次にやるべき課題の提案」** — 具体的に。「Late-Arriving Data のマージ」のようにテーマ名で書き、なぜ今それかも1行添える。**深い層に挙げたテーマと一致させる**
- **「再生できている部分」** — 丸暗記では出てこない箇所の列挙
- **「今回通用した解法」** — 復習モードは「前回通用した解法を封じる制約」を作るので、何で解けたかが分かるように書く（例：「`drop_duplicates` で解けた」）

### 弱点リストの更新を提案する

`GEMINI.md` の「繰り返し出ている弱点」は手で維持されているリストで、**放置すると古くなる。**

同じ種類の指摘が**3タスク以上にまたがった**と判断したら、**`GEMINI.md` への追記を提案する。** 提案だけにとどめ、勝手に書き換えない（リストが膨らむと常時読み込みのコストになる）。

```
`GEMINI.md` の「繰り返し出ている弱点」への追記を提案します：
8. {パターン名} — {判定法や一行の原則}（task{A}・task{B}・task{C} で発生）
```

逆に、**リストの項目が2回連続で問題なく処理されていた**場合は削除も提案する。潰せた弱点を抱え続ける必要はない。

## 英語レビュー

PR 本文が取得できた場合は本文とコミットメッセージの両方、できなかった場合はコミットメッセージのみを対象とし、**どちらなのかを明記する。**

**PRのタイトルも対象に含める。** コミットメッセージ本文だけ見て、タイトルのコロン抜けを見落とした事例がある。

以下を機械的に確認する。

**文法**
- 自動詞を受動態にしていないか（`be remained` ✗ → `be kept` / `will remain`。同型：`be occurred` ✗、`be happened` ✗）。日本語の「〜される」を直訳すると起きる
- 三単現の `-s` の脱落（`This query extract` ✗）。技術文書は主語が三人称単数になりがち
- 助動詞の後は原形（`will makes` ✗ → `will make`）
- 冠詞の欠落（単数可算名詞に冠詞・所有格があるか）。初出の懸念に `the` を付けていないか（`the problem` → `a potential issue`）
- **不可算名詞に複数形を付けていないか**（`any advices` ✗ → `any advice`。同型：`informations` ✗、`feedbacks` ✗）
- 使役動詞の語法（`let X do` / `allow X to do`。`let X to do` ✗）
- 形式目的語の欠落（`makes easy to follow` ✗ → `makes it easy to follow`）
- `recommend` の語法（`recommend you to <名詞>` ✗ → `recommend two actions`）
- 句動詞に余分な前置詞を付けていないか（`work out with solving` ✗ → `work out how to solve`）
- カンマスプライス（独立した2文をカンマだけで接続していないか）

**語彙**
- 技術用語の選択（`temporal` ✗ → `transient`、`row number`（何行目か）✗ → `row count`、`credit` → `credit consumption`）
- 存在しない副詞（`expectedly` ✗ → `as expected`）
- 動詞の強さがコードの挙動と一致しているか（条件で落とすなら `Check if` より `Assert that`）
- 対応する名詞があるのに -ing 形にしていないか（`its requesting` → `its requests`）
- `in maximum` ✗ → `up to` / `a maximum of`
- トーンが強すぎないか（リスク報告に `I'd love to` ✗ → `I would like to flag`）

**表記**
- 頭字語（`api` → `API`、`ai` → `AI`）、クラス名（`runtimeerror` → `` `RuntimeError` ``）
- 曜日・月名は大文字始まり（`monday` ✗ → `Monday`）
- コード識別子はバックティックで囲み、正確に綴る。所有格の `'s` を識別子に付けない（`df_sales's` → `the row count of df_sales`）
- **Conventional Commits のコロン**（`feat(scope) msg` ✗ → `feat(scope): msg`）。**4回連続で見落とされている項目なので必ず確認する**
- type の選択（フィードバック文書の追加は `feat` ではなく `docs`）
- 見出しに文章や句点を入れない
- **スペルミスは git 履歴に残り検索性を損なう**ことを指摘する（マージ済みなら修正不能）

**構成・内容**
- 冒頭1文で「何を・どこに・どういう制約で」を言い切れているか
- 設定値の羅列に「なぜその値か」が添えられているか
- **仕様記述がコードのバグと同じ誤りをしていないか。** 繰り返し起きている。説明と実装が同じ誤りを共有すると、レビュアーが説明を読んでもバグを検出できない
- **仕様記述が課題文の要求とずれていないか**（実例：課題は「0行を返す」だったが PR は「`(0,0)` を返す」と書いていた）
- 期間・範囲は**半開区間の記法**で書けているか（`[2026-08-24 00:00, 2026-08-31 00:00)`）。この記法にするだけで、書いた本人がオフバイワンに気づける
- 「最大値を取る」等の仕様に、**同点時の扱い**が書かれているか
- 制約から逸脱した場合、それが逸脱として明示されているか
- **技術的な誤りが英語の記述から見つかることがある。** 実例：PR に `duplicated values in columns [store_id, received_at]` と書かれていたが、重複粒度は `(store_id, sales_date)` で `received_at` は差異を見分ける列だった。文面の点検が技術的誤解の発見に繋がる

**不確実性の表現**（Note セクションがある場合）

日本語の「厳しいかも」「よく分からなかった」を直訳すると過度に自信がない印象になる。使える型を提示する。

- `I am not confident about X`
- `I could not work out ...`（`I didn't understand` より能動的）
- `I would appreciate a second opinion on ...`
- `I dropped it since it was out of scope`（やらなかった判断の正当化）
- `Working out how to X took me about an hour`（所要時間を事実として述べる）
- `What I had actually got wrong was ...`（自己診断の提示）

**添削は原文と添削版を並べ、変更理由を説明する。** 添削版で直した箇所は、必ず指摘リストにも規則として挙げる（**添削版だけ直して規則を説明しない、という漏れがあった**）。

**穴：** {3段階。深刻度順}

## トーン

- 実務のレビューと同じ厳しさで、遠慮しない
- 弱点を指摘する際も人格や能力を否定せず、「次にどう直すか」を必ず添える
- **過剰な演出をしない**（役割演技、絵文字の多用、「100点満点」のような満点評価）
- **確認していないことを確認したように書かない**

## Pass 2 チェックリスト

書き終えたら確認する。**1つでも「見ていない」があれば戻る。**

- [ ] Pass 1 の出力を読み、重複を避けたか。抜け・誤りがあれば指摘したか
- [ ] 命名の層規約（`raw_` / `stg_` / `fct_` 等）の誤用を確認したか
- [ ] 発動しえない `NVL`/`COALESCE`・冗長な `CASE WHEN` がないか確認したか
- [ ] 確認質問を**2〜3問**書いたか（1問で終わっていないか）
- [ ] 確認質問が、自分や Pass 1 の提案についてではなく提出版について聞いているか
- [ ] 3段階の層の割り当てが深刻度順になっているか（データ破損 > パフォーマンス）
- [ ] まとめに「次にやるべき課題の提案」「今回通用した解法」を書いたか（次回の復習モードが読む）
- [ ] PR **タイトル**も英語レビューの対象に含めたか（Conventional Commits のコロン）
- [ ] 添削版で直した箇所を、指摘リストにも規則として挙げたか
- [ ] 得られなかった入力を明記したか
