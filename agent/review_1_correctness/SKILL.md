# レビュー Pass 1：正確性

リポジトリの前提・フォルダマップ・禁止事項・蓄積した弱点は `GEMINI.md` にある。

## このパスの担当範囲

**このパスは「コードが正しいか」だけを見る。**

| 担当する | 担当しない（Pass 2） |
|---|---|
| 課題の主題の攻略 | イディオム・パフォーマンス |
| 褒めるパート | 可読性・命名 |
| 制約の充足判定 | 確認質問 |
| 正確性（壊れる条件） | まとめ・3段階の穴 |
| 本番運用の必須トレース | 英語レビュー（PR） |
| 修正版スクリプト | |

**PR は取得しない。** 英語レビューは Pass 2 の担当なので、このパスではコードと課題文だけを見る。

終わったら、ユーザーに「Pass 2（品質と伝達）に進むか」を確認する。

---

## 手順

### 0. Pass 1 が既に済んでいないか確認する（最初にやる）

**このスキルを起動した時点で、対象タスクの Pass 1 が既に終わっている可能性がある。** 重複実行を避けるため、必ず確認する。

```bash
ls {タスクフォルダ}/
grep -h "^> 進捗：" {タスクフォルダ}/FB_from_AI_*/README.md 2>/dev/null
```

| 見つかったもの | どうするか |
|---|---|
| 何も無い | **このまま Pass 1 を実行する** |
| `> 進捗：Pass 1（正確性）まで完了` | **Pass 1 を実行しない。** 「Pass 1 は完了済みです。Pass 2（`review_2_quality`）に進みますか」とユーザに伝えて止まる |
| `> 進捗：Pass 1・Pass 2 完了` | **実行しない。** 両パス完了済みであることを伝え、何をしたいか確認する（再レビューなら新しい連番で Pass 1 から） |

ユーザが明示的に「Pass 1 をやり直して」と言った場合のみ、上記に関わらず実行する。その際は**既存フォルダを上書きせず、新しい連番**を使う。

### 1. 対象タスクを確認する

**必ず最初に、どのタスクのフィードバックが欲しいかユーザに確認する。** 勝手に「最新のもの」を選ばない。複数選択もありうる。

選択肢を出すときは、各タスクが何のテーマだったかを1行で添える（ユーザは番号を覚えていない）。**列挙は `ls sql/_daily/` のようにディレクトリ全体を見る**（グロブでは誤字フォルダを取りこぼす）。

### 2. 読み込む

対象タスクについて、以下をすべて読む。**一部だけ読んで書き始めない。**

| 読むもの | 目的 |
|---|---|
| `タスクフォルダ/README.md` | 課題文。要求と**制約**の把握 |
| `タスクフォルダ/` 直下のスクリプト | **提出版。これがレビューの主対象** |
| `タスクフォルダ/setup.sql` | SQLタスクの場合。DDLとサンプルデータ（机上トレースに必要） |
| `FB_from_AI_*/` 等の既存レビュー | 指摘の重複を避ける・反映されたかを見る |
| `タスクフォルダ/FB/`, `answers/`, `answer/` | **過去のタスクにのみ存在する**模範解答。無いのが通常 |

### 3. 課題文の制約を全部列挙する

**レビューを書く前に、課題文の制約を箇条書きで書き出し、1つずつ判定する。**

```
制約1: 動的関数（CURRENT_DATE等）の禁止 → 満たしている
制約2: sale_timestamp カラムを関数で加工しない → 違反（DATEDIFF に渡している）
制約3: ISO週基準 → 満たしている（DAYOFWEEKISO）
制約4: CTEは2段階まで → 違反（3段階）
```

**この列挙を省くと違反を取りこぼす。** 過去に、CTE の段数（制約4）だけを指摘してカラム加工（制約2）を見落とした事例がある。**目立つ制約を1つ見つけた時点で満足せず、全制約を判定する。**

制約違反は**正確性の問題として扱う。** 逸脱してもよいが、その場合は「PR に逸脱として明示し理由を書く」のが作法だと伝える。「除外して数えれば満たしている」という書き方は不可。

---

## 前提：模範解答は存在しない

出題スキルは**模範解答を作らない。** したがって**提出版に書かれているものはすべて本人の自力の産物**で、写した可能性を考慮する必要はない。

これは同時に、**レビュアーが正しさの判断を全責任で負う**ことを意味する。照合できる「正解」が無いので、机上トレースの精度がそのまま品質になる。「模範解答と一致しているから正しい」という近道は使えない。

### 過去のタスクに模範解答がある場合のみ

`FB/` や `answers/` がある古いタスクでは、模範解答を**正解ではなくもう一つのレビュー対象として読む**（既知の欠陥は `GEMINI.md` を参照）。

- 既存FBが**既に指摘済みの点は繰り返さない**（「既存FBの指摘は正しい」と一言触れて次へ）
- 既存FBが**見落としている点を探す**
- **模範解答のコードについても「壊れる条件を1つ挙げる」を実行する。** 挙げられないなら検証していないのと同じ
- 既存FBの**断定が過剰でないか**を検証する（実例：「スカラサブクエリなのでプルーニングが100%効く」は、オプティマイザの定数畳み込みに依存する話で保証はない）
- 評価が異なる場合は、そう明言して理由を書く

**新しいタスクには存在しないので、「既存FB未指摘」のような見出しも使わない**（比較対象が無いのに未指摘と書くと、読み手が存在しないFBを想像する）。

## 課題の主題と、その攻略（最初に書く）

**課題文が「罠」「難所」「死の罠」「最も難しい」などと明示しているテーマを特定し、それが攻略できているかを最初に書く。**

課題は必ず何かを狙って作られている。そこを攻略できていれば、それが最大の成果である。そこに触れずに細部だけ書くと、レビューとして焦点を外す。

過去の実例：課題文が「毎年必ずどこかでバグを発生させる死の罠」としてカレンダー年とISO年の不整合を挙げていたタスクで、提出コードは**週番号を一度も materialise しない方針**を採ったため構造的に免疫があった。この評価が抜けていたレビューがあった。

攻略できていない場合も、まず主題について書く（正確性の節で扱う）。

---

## 褒めるパート

**課題文が要求した以上の判断が入っている箇所**を探す。具体的なコード行を引用し、「なぜ良いのか」と**なぜそれが自力の証拠なのか**を書く。

- **課題文のヒントに乗らず、別の正解に到達している**（例：`idxmax()` を使えと誘導されたのに `sort_values` + `drop_duplicates` で解いた）
- **便利メソッドを知らずに、プリミティブだけで解き切っている**（冗長でも組み立てた力は明確に評価する）
- **公式ドキュメントを読んだ形跡**（例：`validate="many_to_one"` ではなく短縮エイリアス `validate="m:1"`）
- **副作用や境界を先読みした形跡**（`.copy()` の位置、半開区間の選択、`DAYOFWEEKISO` の選択、境界への `DATE_TRUNC` など）
- **過去の指摘が反映されている箇所。** 前回のレビューで指摘した内容を、言われずに次のタスクで適用していたら必ず挙げる。**これを見落としたレビューがあった**（`DATE_TRUNC` の教訓を自主的に適用していたのに触れなかった）
- **課題の主題を構造的に回避する方針を選んでいる**

「素晴らしい」だけで終わらせない。常に「どこが」「なぜ」を伴わせる。**謙遜しがちなので遠慮せずはっきり褒める。** 自己評価が実態より厳しいと判断できる場合は、そう明言する。

## 正確性

### 「壊れる条件」を必ず書く

「〜の可能性があります」で終わらせない。**具体的な入力 → 何が起きるか**を書く。書けないなら、その指摘は弱いので出さない。

**サンプルデータがある場合は、具体的な行ID・タイムスタンプ・値で示す。**

```
✗ 時刻成分が残るため、意図しないオフバイワンを引き起こすリスクがあります
✓ SESSION_DATE = '2026-09-01 03:15:00' のとき境界は 2026-08-24 03:15:00 になり、
  S_002（2026-08-24 01:10:00、月曜未明の売上）は 01:10 < 03:15 で除外される。
  エラーは出ず、合計金額だけが毎週小さくなる
```

前者は読んでも何をすべきか分からず、後者は再現手順とテストケースを兼ねる。

**サンプルデータで露見しないバグを特に疑う。** 提出版がサンプルでは正しく動いても、1行足すと壊れる構造になっていることがある（例：`partition by store_id` のみの重複排除は、1店舗が複数日付の行を持った瞬間にデータが欠損する）。

### 「検証が機能していない」パターンを毎回確認する

実装で使った操作と同じ操作で期待値を計算していると、両辺が必ず一致し、検証は「実装が実装どおりであること」しか確認しない。

判定法：**その検証が失敗する入力を1つ挙げられるか。** 挙げられないなら機能していない。

実例：`validate="m:1"` が通った後の行数アサーション（数学的に失敗不能）。`drop_duplicates` の結果同士を比較するアサーション（ソート順は件数を変えないので失敗不能）。

指摘するときは**通ってしまう改変を具体的に示す**（「`ascending=False` を `True` にすると全キャンペーンで最小値が出るが、行数は変わらないので検証は通る」）。

### 修正指示の副作用を検証する

**既存FBや自分が出す修正案について、「その指示だけに従ったら何が起きるか」を必ずトレースする。**

過去の実例：既存FBが「`>=` と `<` の半開区間に直せ」と指示していたが、境界に `DATE_TRUNC` が無い状態でそれだけ適用すると、実行時刻が深夜0時でない本番環境で月曜未明の売上が毎週サイレントに欠損する。**修正指示が別のバグを生むケースは、単独のバグより検出が難しい。**

**自分の修正案が、既存の防御を外していないかも確認する。** 例：単一日付への `WHERE` を足したことで `partition by store_id` だけで足りるようになる場合、それは正しいが、**期間指定に一般化した瞬間にバグが復活する。** 「防御を外した」ことを明示するか、外さない形（`partition by store_id, sales_date` と早期フィルタの併用）を勧める。

### 指摘には必ず「次にどう直すか」を添える

修正コード片と、持ち帰れる一般原則（「`df.index` をデータとして使う前に `reset_index(drop=True)`」など）をセットで書く。

## 本番運用の視点（必須トレース）

**以下3点は毎回明示的にトレースする。トレースせずに「問題なし」と書いてはならない。**

### 1. 入力が0件のとき、何行返り、その中身はどうなるか

- SQL：`GROUP BY` の無い集計クエリは**0行入力でも必ず1行返す。** 集計関数は NULL になるため `(NULL, NULL)` が出力される。下流で主キー・パーティションキーに使っていれば落ちる。対処は `COALESCE(SUM(x), 0)` と、ラベルを集計関数から取らないこと
- Python：空の DataFrame が静かに返って「正常終了」しないか。上流の連携停止を検知できるか

### 2. 同じ処理を再実行したとき、同じ結果になるか（冪等性・決定論性）

- 同点（tie）時にどの行が選ばれるか決まっているか。`sort_values` の既定 `kind='quicksort'` は非安定。SQL の `ROW_NUMBER` もソートキーが同値なら非決定的
- 実行時刻・実行曜日に依存していないか
- 出力の行順・index が固定されているか

### 3. 過去の特定期間を対象に再実行（バックフィル）できるか

- 「実行日から逆算」する構造は、**実行が1週遅れると対象期間ごとずれる**
- 対象期間を外から渡せる設計（セッション変数、dbt の `var()`、Airflow の論理実行日）になっていれば問題なし。**渡せるなら「問題なし」と書いてよい**（変数化されているのに欠陥として書いた誤りがあった）

### そのほか

エラーハンドリング、終了コード（握りつぶして 0 を返していないか）、ログ、リトライ設定値、`assert` を品質ゲートに使っていないか（`python -O` で消える）、宣言されていない依存、境界そのものを検証するアサーションの有無。

### 「問題なし」と書く前に、確認した内容を書く

```
✗ ### 本番運用の視点
  問題なし

✓ ### 本番運用の視点
  0件入力・再実行・バックフィルの3点をトレースした結果、以下2件が該当する。
```

確認せずに「問題なし」と書くのは、見落とすことより悪い。**見ていない領域を検証済みとして報告することになる。**

### 修正版スクリプトは必ず出す

**指摘だけで終わらせず、修正版スクリプトを同じフォルダに必ず置く。**

- **指摘した全項目を同時に満たす形**にする。個別の修正案を並べるのと、全部を両立させる1本を書くのは別の作業で、後者の方が難しく学習価値も高い
- 課題文の**制約も満たす**（CTE段数などを数え直す）
- **元のスクリプトとの差分を冒頭コメントに列挙し、それぞれ理由を書く**
- **差分として挙げるのは、実際に変更した行だけ。** 元コードに存在しなかった記述を「修正した」「削除した」と書かない。変更していない行を差分に混ぜると読み手が元コードを誤解する
- **実行していないことを明記する**
- SQL の場合、**`SET` 文に依存する解は単一 SELECT にならないため dbt モデルには移植できない**

## トーン

- 褒めるパートは温かく具体的に。正確性のパートは実務のレビューと同じ厳しさで、遠慮しない
- 弱点を指摘する際も人格や能力を否定せず、「次にどう直すか」を必ず添える
- **過剰な演出をしない**（役割演技、絵文字の多用、「100点満点」のような満点評価）
- **確認していないことを確認したように書かない。** 実行していない、トレースしていない——正直に書く
