# 💻 シニア・データエンジニア（テックリード）からの挑戦状

## 今回選んだテーマ： Window関数とQUALIFY句による複雑な重複排除（CTE禁止）

---

### 業務要件（シナリオ）

あなたは急成長中のグローバル配車サービス「SlickRide」のテックリード（シニア・データエンジニア）です。

現在、乗車のステータス更新データをリアルタイムにストリーミングインジェクションするCDC（Change Data Capture）パイプラインを運用しています。このデータは、生データレイヤーのテーブル `raw_ride_updates` に直接蓄積されています。

しかし、アップストリーム（モバイルアプリやサーバー側）における急激なネットワーク瞬断やリトライ処理、バッチ送信処理の影響により、実務上極めて泥臭い以下のような**データ整合性の課題（エッジケース）**が発生しています。

1. **同一日時（ミリ秒単位まで同一）の重複データ**:
   同じ乗車ID（`ride_id`）に対して、まったく同じタイムスタンプ（`updated_at`）を持つレコードが複数同時にインサートされることがあります。
2. **ステータスの逆転・混在可能性**:
   ミリ秒単位まで完全に同一のタイムスタンプで、異なるステータス（例：一方が `ACCEPTED`、もう一方が `ARRIVED`）が書き込まれるケースがあります。この場合、業務ドメインにおける以下のステータス優先度（ライフサイクルの進捗度）に従って、最も進んでいるレコードを「最新の真実（Latest State）」として判定する必要があります。
   * **ステータス優先度（低 → 高）**: `REQUESTED` -> `ACCEPTED` -> `ARRIVED` -> `PICKED_UP` -> `COMPLETED`（または `CANCELLED`）
3. **完全な物理重複の存在**:
   同一 `ride_id`、同一 `updated_at`、同一 `ride_status` で、システム上の内部シーケンスIDである `system_record_id` のみが異なる完全な重複レコードも存在します。この場合は、より大きい `system_record_id` を持つレコードを最新として採用（タイブレーク）してください。
4. **重複検知用の監査カラム要件**:
   データ品質監視チームから、「**最新レコードとして抽出されたその日時の時点で、実際に同一タイムスタンプによる重複（または競合）レコードが複数存在したか**」を監視するための監査カラム `is_duplicate_at_timestamp` (BOOLEAN型) を付与してほしいと強い要望がありました。これは、最新と判定された日時と同じ日時に、該当 `ride_id` のレコードが2件以上存在していた場合に `TRUE` とし、単一ユニークであった場合は `FALSE` と判定するものです。

---

### 制約条件 & テックリードからの要求：

本番環境のデータ量が数十億件規模に肥大化していることを考慮し、クエリコンパイル時の最適化オーバーヘッドを最小限に抑え、かつウェアハウスのメモリ管理（Spillage）を徹底的に防ぐため、以下の厳しい制約を課します。

1. **CTE（`WITH` 句）の全面禁止**:
   dbt開発者によく見られる「5段階のCTEをチェイニングして中間結果を何度も処理する」ような記述は一切禁止します。すべての処理は、**単一のフラットな `SELECT` 文のみ**で完結させてください。
2. **インラインサブクエリの禁止**:
   `SELECT` 内や `WHERE`、`QUALIFY` 句の中で `(SELECT MAX(...) ...)` や `EXISTS (SELECT ...)` のような相関・非相関サブクエリを入れ子にすることを禁止します。
3. **Snowflake特有の `QUALIFY` 句をネイティブに使用すること**:
   サブクエリで `ROW_NUMBER() = 1` を囲んで外側でフィルターするのではなく、`QUALIFY` 句を最上位（Top-level projection）で直接使用し、Snowflakeオプティマイザの **Top-K 最適化（インメモリでのハッシュマップ追跡によるソート処理の完全なスキップ）** をトリガーしてください。これにより、メモリ消費量を \\(O(N \log N)\\)（全体ソート）から \\(O(N)\\)（ユニーク乗車ID数）に削減します。
4. **決定論的（Deterministic）なクエリ設計**:
   重複レコードをタイブレークする際、並び順に曖昧さ（非決定性）が残らないよう、必ず一意な列による完全なタイブレーク条件を記述してください。

### テーブル定義（DDL & サンプルデータ）

以下のDDLとDMLを実行してテスト環境を準備してください（Snowflake互換SQL）。

```sql
-- テスト用データベース・スキーマの設定
CREATE OR REPLACE TRANSIENT TABLE raw_ride_updates (
    system_record_id INT,
    ride_id VARCHAR,
    passenger_name VARCHAR,
    updated_at TIMESTAMP_NTZ,
    ride_status VARCHAR,
    fare_amount DECIMAL(10,2)
);

-- テストデータのインサート
INSERT INTO raw_ride_updates (system_record_id, ride_id, passenger_name, updated_at, ride_status, fare_amount) VALUES
-- ケース1: 通常の時系列更新（正常系。最新の 2026-08-23 10:15:00 が選ばれるべき）
(1001, 'RIDE_001', 'Alice', '2026-08-23 10:00:00', 'REQUESTED', 15.00),
(1002, 'RIDE_001', 'Alice', '2026-08-23 10:05:00', 'ACCEPTED', 15.00),
(1003, 'RIDE_001', 'Alice', '2026-08-23 10:15:00', 'PICKED_UP', 18.50),

-- ケース2: 同一時刻でのステータス競合（RIDE_002 の 11:00:00 に2レコード存在。優先度の高い ARRIVED が選ばれ、監査カラムは TRUE となるべき）
(1004, 'RIDE_002', 'Bob', '2026-08-23 10:55:00', 'REQUESTED', 22.00),
(1005, 'RIDE_002', 'Bob', '2026-08-23 11:00:00', 'ACCEPTED', 22.00),
(1006, 'RIDE_002', 'Bob', '2026-08-23 11:00:00', 'ARRIVED', 22.00),

-- ケース3: 同一時刻・同一ステータスでの完全な物理重複（RIDE_003 の 12:30:00。より大きい system_record_id = 1009 が選ばれ、監査カラムは TRUE となるべき）
(1007, 'RIDE_003', 'Charlie', '2026-08-23 12:00:00', 'REQUESTED', 30.00),
(1008, 'RIDE_003', 'Charlie', '2026-08-23 12:30:00', 'COMPLETED', 35.00),
(1009, 'RIDE_003', 'Charlie', '2026-08-23 12:30:00', 'COMPLETED', 35.00),

-- ケース4: 過去履歴に重複があるが、最新タイムスタンプ時点では単一レコード（RIDE_004。最新の 14:10:00 自体は重複していないため、監査カラムは FALSE となるべき）
(1010, 'RIDE_004', 'David', '2026-08-23 14:00:00', 'REQUESTED', 10.00),
(1011, 'RIDE_004', 'David', '2026-08-23 14:00:00', 'ACCEPTED', 10.00),
(1012, 'RIDE_004', 'David', '2026-08-23 14:10:00', 'COMPLETED', 12.00);
```
