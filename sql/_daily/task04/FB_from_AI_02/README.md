## 課題の主題と、その攻略
課題が「毎年必ずどこかでバグを発生させる死の罠」として挙げたカレンダー年とISO年の不整合（2025-12-29問題）に対して、**週番号を一度も materialise せず、基準日からの引き算だけで着地させる構造を選んだことで、年境界の罠を完全に無力化しています。** この設計の骨格は完璧に攻略できています。

## 良かったところ
### 1. `DAYOFWEEKISO` の選択と引き算のロジック — 完全に自力の判断
```sql
dateadd(day, -(DAYOFWEEKISO($SESSION_DATE) - 1) - 7, $SESSION_DATE)
```
環境依存の `DAYOFWEEK` ではなく `DAYOFWEEKISO` を選び、曜日ずれを吸収する `- (dow - 1)` と、前週へ戻る `- 7` を分けて書いたことで、「月曜実行でも火曜実行でも揺らがない」という要件を完璧に満たしています。模範解答と完全に一致するこのロジックを、制約下で自力で組み上げたのは見事です。

### 2. 将来のリスク分析と提案 — プロフェッショナルな姿勢
PR本文で、全件スキャンによるクレジット消費増大のリスクを指摘し、Clustering Key と dbt incremental model の2つの解決策を提案しています。単にクエリを書くだけでなく、そのクエリが運用環境でどう振る舞うかを先読みする視点は素晴らしいです。

## 制約の充足
- **制約1: 動的関数の禁止** → 満たしている（`$SESSION_DATE` を使用）
- **制約2: Sargable な範囲指定** → 違反（`datediff` で `sale_timestamp` を加工）
- **制約3: ISO週基準** → 満たしている（`DAYOFWEEKISO`）
- **制約4: CTEは2段階まで** → 違反（`base`, `raw_get_baseline`, `raw_extract_targets` の3段階。「`base` を除外して」は逸脱です）

### 本番運用の視点
#### ① 【既存FB未指摘】生の `TIMESTAMP` への Clustering Key 設定はアンチパターン
PR本文で提案いただいた Clustering Key についてです。
```text
1. For Extract data -> Add CLUSTERING KEY, this helps query engine...
```
着眼点は100点ですが、**生の `sale_timestamp`（TIMESTAMP_NTZ）にクラスタリングキーを張るのは Snowflake のアンチパターン**です。タイムスタンプはミリ秒単位で値がばらつく（高カーディナリティ）ため、マイクロパーティションが細かく分割されすぎ、自動クラスタリングの維持・再編成コスト（クレジット）が跳ね上がります。（AIすらスルーして絶賛していましたが、実務ではデータ基盤チームからストップがかかります）

**次にどうするか：** `DATE(sale_timestamp)` のように、日付レベルで粒度を丸めた式をクラスタリングキーに指定してカーディナリティを下げる。

#### ② 【Claude未指摘】 `SET` に依存した境界値は dbt モデルに移植できない
Claude のレビュー（`FB_from_Claude_01`）では、「プルーニングを確実にするため、境界値の計算そのものを `SET WEEK_START = ...` のようにセッション変数に出すべき」と提案されています。

しかし、**この指示に従うと要件にある dbt のモデルとして動かなくなります。** dbt のモデルは原則として「単一の `SELECT` 文」でなければならず、モデル内で `SET` を連発することはできません。したがって、境界値の計算はやはり CTE 内で行い、クエリ1本で完結させる（`FB/` の模範解答の構造）のが実務（dbt）における正解です。

### 正確性
#### ③ dbt での `USE SCHEMA`
```sql
USE SCHEMA MUSCLE_DB_TASK04.RAW;
```
クエリ内に `USE SCHEMA` がハードコードされています。dbt では接続スキーマは `profiles.yml` やマクロが動的に管理するため、モデル内に書くとデプロイ先（開発環境/本番環境）の切り替えが壊れます。

### イディオム・パフォーマンス
#### ④ 【既存FB未指摘】 1行に集約される `MIN`
```sql
select MIN(baseline) as week
```
すでに `baseline` は全行で同じ値（先週月曜）なので、`MIN` で集約する必要はありません。ですが、`GROUP BY` を使わない全体集計で定数を SELECT に含めるには集計関数（またはスカラサブクエリ / `ANY_VALUE`）で括る必要があります。
これをスッキリ書き、さらに0件入力時の `(NULL, NULL)` 問題も同時に解決できるのが、修正版に記載した **`LEFT JOIN` による境界ベース集計**です。
