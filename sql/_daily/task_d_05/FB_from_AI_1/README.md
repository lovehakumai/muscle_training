## 正確性

### ① PARTITION BY の粒度不足による別日付のデータ欠損
```sql
qualify row_number()over(partition by store_id order by received_at desc) = 1
```
重複排除のパーティションキーに `sales_date` が含まれていないため、同じ店舗が複数の日付でデータを持っていた場合、一番最後に受信した1件のレコードしか残りません。

例えば、`store_A` が '2026-08-31' と '2026-09-01' の両方のデータを送信してきた場合、`received_at` が新しい方（ここでは9月1日）だけが残り、'2026-08-31' のデータは抽出条件にかかわらずこの CTE の段階で消失してしまいます。課題文の「同じ `store_id` と `sales_date` の組み合わせで」という条件に合わせる必要があります。

**次にどうするか：** `PARTITION BY store_id, sales_date` とし、日付ごとの店舗をキーとして重複排除します。

### ② 到達不能な NVL 関数
```sql
select 
    NVL(sales_date, $target_dt) as sales_date
    , NVL(sum( amount ), 0) as amount
from latest_sales_date
where sales_date = $target_dt
group by sales_date
```
`GROUP BY sales_date` を使っているため、抽出対象のデータが0件の場合、この `SELECT` 句自体が評価されず（行が作られず）そのまま 0行 が出力されます。そのため、ここで設定した `NVL(..., $target_dt)` や `NVL(..., 0)` が発動して代替値を出力することはありません。また、`WHERE` 句で `sales_date = $target_dt` で絞り込んでいるため、`sales_date` が `NULL` の行が集計対象に入ることもありません。

**次にどうするか：** 単純に `sales_date` と `sum(amount)` を SELECT します。

## 本番運用の視点
0件入力・再実行・バックフィルの3点をトレースした結果、以下1件が該当します。

- **0件入力**: 問題なし。`GROUP BY sales_date` によって、対象データがない場合は期待通り 0行 が返ります。
- **再実行（決定論性）**: `QUALIFY` 内の `ORDER BY received_at DESC` において、全く同じ `received_at` のレコードが2件届いた場合、どちらが採用されるかは非決定的です（金額が変わる可能性があります）。ただし、元データにこれ以上の一意キーが存在しないため、これはデータモデルの欠陥であり、クエリ側で中立なタイブレーカーを選ぶことはできません（業務側で「金額が大きい方を正とするか」などを決める必要があります）。
- **バックフィル**: 問題なし。`SET` 変数を用いて対象日を外から渡せる設計になっており、過去日付での再実行が可能です。

## イディオム・パフォーマンス

- **窓関数の前の絞り込み（フルスキャンの回避）**: CTE `latest_sales_date` の中で抽出条件 (`WHERE sales_date = $target_dt`) を指定していないため、全日付・全店舗のデータをフルスキャンしてソート・重複排除を行ってから、外側のメインクエリで1日分に絞り込んでいます。対象日が決まっている場合は、**CTEの中で窓関数（QUALIFY）を適用する前に WHERE で絞り込む**のが鉄則です。
興味深いことに、もし CTE 内で `WHERE sales_date = $target_dt` を行っていれば、対象データは1日分に限定されるため、Pass 1で指摘された「`PARTITION BY` に `sales_date` がない」というデータ欠損バグも実質的には顕在化しませんでした。

## 可読性・命名

- **実体と合わない命名**: CTE名 `latest_sales_date` は「最新の売上日（単一の要素）」のように読めますが、実体は「各店舗の最新の売上レコード群」です。粒度と型が名前に入っていません。`latest_sales_records` や `deduplicated_sales` のように、中身を正確に表す名前にする必要があります。
