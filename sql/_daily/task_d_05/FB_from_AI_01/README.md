## 正確性

### ① PARTITION BY のキー不足による他日付データの欠損（サンプルで露見しないバグ）
現状のコード：
```sql
qualify row_number()over(partition by store_id order by received_at desc) = 1
```
**壊れる条件：**
この `QUALIFY` は「全期間の中で、その店舗の最新1件」だけを残す挙動になっています。
提供されたサンプルデータは「1店舗につき1つの日付」しか持たないため正常に動いているように見えますが、実務において **1つの店舗が複数日付の売上データを持った瞬間にデータが欠損します。**

例えば、以下のように `store_A` が2日分のデータを持っていたとします。
- `store_A`, `2026-08-31` (received_at: 20:00)
- `store_A`, `2026-09-01` (received_at: 20:00)

現状のコードでは `store_id` 単独でパーティションを切っているため、上記のうち最新である `2026-09-01` の行だけが生き残り、`2026-08-31` のデータは CTE の時点で消滅します。もし集計対象日を '2026-08-31' にして実行すると、本来存在するはずのデータが消えているため、合計が 0件として出力されてしまいます。

**次にどうするか：**
「同じ店舗の、同じ日付の中で」重複排除するために、パーティションキーに `sales_date` を追加します（`partition by store_id, sales_date`）。また、対象日の絞り込み（`WHERE`）を CTE 内で先に行うことで、全期間の Window 関数実行を回避できパフォーマンスも劇的に向上します。

### ② NVL のデッドコード化
現状のコード：
```sql
select NVL(sales_date, $target_dt) as sales_date, NVL(sum( amount ), 0) as amount
```
**壊れる条件（バグではなく不要なコード）：**
`GROUP BY` を使用しているため、入力が0件のとき出力は「0行」になります。つまり、1行も出力されないため、この `SELECT` 句の中の `NVL` が評価される機会自体が存在しません（0行のデータに対して関数は適用されません）。あっても害はありませんが、`GROUP BY` が既に守ってくれているため外して構いません。

## 本番運用の視点

- **0件入力の挙動**: トレース済み。対象日付のデータが1件もない場合でも、`GROUP BY sales_date` によって安全に 0行が返ります。問題ありません。
- **再実行・冪等性**: ✗ 同点時の挙動が非決定的です。`ORDER BY received_at DESC` のみであるため、万が一システム障害等で「全く同じ `received_at` のレコードが2件」発生した場合、どちらが選ばれるか保証されず、再実行のたびに集計値が変わるリスクがあります（タイブレーカーとして `amount DESC` などを追加して決定的にする必要があります）。
- **バックフィル**: トレース済み。`$target_dt` によって外部から対象期間を渡せる構造になっているため、問題なく過去分の再実行が可能です。

## 修正版スクリプト

```sql
-- ======================================
-- [変更点]
-- 1. QUALIFY の PARTITION BY に sales_date を追加（他日付データの欠損防止）
-- 2. QUALIFY の ORDER BY に amount DESC を追加（同点タイムスタンプ時の非決定性排除）
-- 3. 対象日（$target_dt）の絞り込みを CTE 内に移動（Window関数の対象行数を減らしパフォーマンス向上）
-- 4. GROUP BY により無効化されている NVL を削除
-- ※ 机上トレースによる修正であり、実行確認はしていません。
-- ======================================
SET raw_target_dt = '2026-09-01 00:00:00'::TIMESTAMP_NTZ;
SET target_dt = date_trunc('day', $raw_target_dt);

with latest_sales_date as (
    select
        store_id
        , sales_date
        , amount
        , received_at
    from raw_daily_sales
    where 
        sales_date = $target_dt
    qualify
        row_number() over(partition by store_id, sales_date order by received_at desc, amount desc) = 1
)
select 
    sales_date
    , sum( amount ) as amount
from 
    latest_sales_date
group by sales_date
;
```

## イディオム・パフォーマンス

- **不要な全期間スキャン（スピレージのリスク）**
  `WHERE sales_date = $target_dt` が CTE の外（メインクエリ）に置かれています。これにより、CTE 内の `QUALIFY` では「全期間の全データ」に対して Window 関数（`ROW_NUMBER`）が実行されてから、最後に1日分だけが残る形になっています。対象日の絞り込みは必ず Window 関数の前（CTE の中）で行う必要があります。
- **発動しない `NVL`**
  メインクエリに `NVL(sales_date, ...)` や `NVL(sum(amount), 0)` が書かれていますが、これらは `GROUP BY` を通るため、0件入力時は「0行」となり評価すらされません。意図した通りには動かず、冗長な記述となっています。

## 可読性・命名

- **CTE名が実体を反映していない**
  `latest_sales_date` という名前は「最新の販売日」という単一の値を連想させますが、中身は「各店舗の最新レコードの集合」です。`latest_store_records` や `deduped_sales` のように、レコードの粒度を示す名前にすると誤解を防げます。
- **定型コメントの残骸**
  冒頭の `[SET VARIOUS]` のコメントが以前の課題からそのままコピーされているようです。「なぜこの変数が必要か」を自分の言葉で書くことで、丸暗記から抜け出せます。
