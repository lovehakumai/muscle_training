# task_d_05 レビュー（遅延データのハンドリングと0件入力の回避）

対象：`my_answer.sql`、PR #8 `feat(pipeline) create answer on task_d_05`

> 注記：コードは実行せず、机上トレースと静的読解で評価しています。

## 課題の主題と、その攻略
課題の主題は「遅延データに対する QUALIFY での重複排除」と、「集計対象日にデータがなかった場合の 0件入力の罠（(NULL, NULL) を出さずに0行を返す）」の2点でした。

これに対して、QUALIFY の構文を正しく組み立て、また `GROUP BY sales_date` を付与することで 0件入力の罠を構造的に回避できており、課題の狙いをしっかり攻略できています。

## 良かったところ
### 1. GROUP BY による 0件入力の回避 — 構造による防御
```sql
select 
    NVL(sales_date, $target_dt) as sales_date
    , NVL(sum( amount ), 0) as amount
from 
    latest_sales_date
where 
    sales_date = $target_dt
group by sales_date
```
PR本文には「(NULL, NULL) ではなく (0, 0) を返そうとして NVL を書いたが動かなかった」と書かれていますが、**課題の要求は「(0, 0) を返す」ことではなく「0行が返るようにする」こと**でした。
そして、このクエリは実際に**0行を返します**。`SUM` だけでなく `GROUP BY sales_date` を付与したことで、「入力が0件ならグループも0個になり、結果も0行になる」という SQL の原則が働き、意図せずとも正解の挙動を達成しています。
`NVL` は結果的に不要でしたが、`GROUP BY` を付けた判断が `(NULL, NULL)` の罠を見事に回避しています。

## 制約の充足
- 制約1: QUALIFY句を使用 → 満たしている
- 制約2: CTEは1段階まで → 満たしている
- 制約3: 0件入力時に(NULL, NULL)ではなく0行を返す → 満たしている（`GROUP BY` によって達成）
- 制約4: 最終結果の順序を保証しない無意味な ORDER BY を書かない → 満たしている

## 技術的な評価

ここからは実務目線のレビューです。

### 正確性
#### ① QUALIFY の PARTITION BY の粒度
```sql
    qualify
        row_number()over(partition by store_id order by received_at desc) = 1
```
ここが今回一番のバグ（データのサイレント欠損）を引き起こす箇所です。`partition by store_id` のみで区切っているため、「すべての日付をまたいで、各店舗の最も新しい1件」しか残りません。

**壊れる条件：**
`store_B` の `2026-09-01` の売上が存在し、かつ `2026-09-02` の売上も存在する場合。
CTE 内の `ROW_NUMBER` は日付に関係なく `store_B` の中で最も新しい `2026-09-02` のレコードだけに `1` を振ります。その結果、`2026-09-01` のレコードは CTE の段階で消滅し、外側の `WHERE sales_date = $target_dt` で `2026-09-02` も弾かれるため、**売上があったはずの 2026-09-01 の `store_B` のデータが完全に欠損します。**

**次にどうするか：**
重複排除は「店舗 × 日付」単位で行う必要があります。`partition by store_id, sales_date` とするか、後述のパフォーマンスの観点で `WHERE` を CTE 内に入れます。

### イディオム・パフォーマンス
#### ① 巨大なテーブルでの全件ソート（Spillageの危険）
現状のクエリは、`raw_daily_sales` の**過去から未来すべてのデータ**に対して `ROW_NUMBER` を計算（全件スキャン・全件ソート）してから、一番外側で `sales_date = $target_dt` に絞っています。実務で数年分のデータがあるテーブルにこれをやると、ウェアハウスのメモリが溢れてディスクへの Spillage が発生し、クエリが著しく遅延、あるいはタイムアウトします。

**次にどうするか：**
`WHERE sales_date = $target_dt` を CTE の **中**（`QUALIFY` より前）に入れます。これにより、オプティマイザが対象日のデータだけをスキャンし、その少ない行数だけで重複排除を行うため、劇的に高速になります。

### 可読性・命名
#### ① 実行されない NVL （Dead code）
`GROUP BY` が0行を返すため、`NVL` が `NULL` をキャッチすることはありません（評価自体がされません）。また、仮に1行返ったとしても、`WHERE sales_date = $target_dt` で絞っているため `sales_date` が `NULL` になることはありません。
**次にどうするか：** 不要な `NVL` は外し、シンプルな `sales_date, sum(amount) as amount` にします。

### 本番運用の視点
0件入力・再実行・バックフィルの3点をトレースした結果、以下2件が該当します。

- **0件入力**: `GROUP BY sales_date` によって正しく 0 行が返るため問題なし。
- **再実行（決定論性）**: `received_at` が同点のレコードが来た場合、`order by received_at desc` だけではどちらが `1` になるか非決定的です。確実に決めるなら一意なIDを第2ソートキーに入れます（今回はテーブルにIDがないため許容範囲です）。
- **バックフィル**: 変数 `$target_dt` を外から渡せる構造になっており、特定日の再集計が容易な優れた設計です。
